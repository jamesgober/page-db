# page-db v0.4.0 — The Allocator, and the Feature Freeze

**The id space, managed — and the API frozen for 1.0.** v0.4.0 adds the last
piece of the v0.x surface: a page-id allocator with an on-disk free-list, sitting
beside the buffer pool over the same file. With it in place the public API is
complete and **feature-frozen**; the remaining road to 1.0 is hardening, not new
surface. Purely additive — the page, file, and pool APIs are unchanged.

## What is page-db?

The paging substrate beneath B-tree and heap storage engines. The
[`PageFile`](../API.md#pagefile) is the durable foundation, the
[`BufferPool`](../API.md#bufferpool) is the cache on top, and now the
[`PageAllocator`](../API.md#pageallocator) manages which ids are in use — the
three together are what a storage engine builds on.

## What's new in 0.4.0

### `PageAllocator` — hand out and reclaim ids

`PageAllocator<S = PageFile>` turns the flat array of page slots into a managed
id space: [`allocate`](../API.md#pageallocator) returns an unused id,
[`free`](../API.md#pageallocator) returns one for reuse.

```rust
use page_db::{PageAllocator, DEFAULT_PAGE_SIZE};

# fn main() -> Result<(), page_db::PageError> {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
let alloc = PageAllocator::open(&path, DEFAULT_PAGE_SIZE)?;

let a = alloc.allocate()?;   // 1
let b = alloc.allocate()?;   // 2
alloc.free(a)?;              // a goes on the free-list
let c = alloc.allocate()?;   // reuses a
assert_eq!(c, a);
assert_ne!(c, b);
alloc.sync()?;               // persist the allocator state durably
# Ok(())
# }
```

Reuse is tracked with a free-list and a high-water mark for ids never yet handed
out. Both `allocate` and `free` are **pure in-memory operations** — no I/O on the
hot path; the development-machine numbers are ~8 ns for a fresh allocation and
~16 ns for an allocate/free cycle that recycles a freed id.

### The on-disk free-list

On disk the free-list is an intrusive chain: each free page stores the id of the
next free page in its first eight bytes, with the chain head, the high-water
mark, and the free count in a **superblock** at page 0, which the allocator
reserves (so the ids it returns start at 1). [`sync`](../API.md#pageallocator)
writes the chain and the superblock, then flushes the store. Because the hot path
is in memory, the allocator's durability follows the same checkpoint discipline
as everything else: persist the allocator as part of the checkpoint that makes
the pages it handed out durable. As ever, the write-ahead log above is the
authority on crash recovery; the superblock is a checkpoint of allocator state.

### Composing the allocator and the pool

A storage engine needs both the allocator and the pool over the *same* file. The
new `PageStore for Arc<S>` impl makes that direct: wrap the file in an `Arc` and
give a clone to each.

```rust
use std::sync::Arc;
use page_db::{BufferPool, PageAllocator, PageFile, DEFAULT_PAGE_SIZE};

# fn main() -> Result<(), page_db::PageError> {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
let store = Arc::new(PageFile::open(&path, DEFAULT_PAGE_SIZE)?);
let alloc = PageAllocator::new(Arc::clone(&store))?;
let pool = BufferPool::new(Arc::clone(&store), 128);

let id = alloc.allocate()?;
let guard = pool.new_page(id)?;
guard.write().payload_mut()[0] = 0x7;
pool.flush_all()?;
alloc.sync()?;
# Ok(())
# }
```

### Direct I/O hardening

Direct I/O is now exercised across page sizes from 4 KiB to 64 KiB, confirming
the buffer, the length, and the file offset stay block-aligned as the size
changes — not just at the 4 KiB default. An end-to-end test drives the allocator
and the pool over one shared file and reopens it to confirm both the ids and the
page data survive.

### Verifying the allocator

- A **property test** asserts that through any sequence of allocates and frees,
  no id is ever handed out twice while live, and the free count tracks a
  reference model exactly.
- A **reopen test** confirms the high-water mark and free-list survive a sync and
  reopen.
- A **`loom` model check** confirms concurrent allocations never collide.

## Feature freeze

The public API is **frozen for 1.0**. Every type, method, and error variant a
1.0 consumer will use is present:
[`PageFile`](../API.md#pagefile)/[`PageFileOptions`](../API.md#pagefileoptions),
[`BufferPool`](../API.md#bufferpool)/[`PageGuard`](../API.md#pageguard-pageref-pagemut),
[`PageAllocator`](../API.md#pageallocator), [`PageStore`](../API.md#pagestore),
[`Page`](../API.md#page), the value types, and
[`PageError`](../API.md#pageerror--pageresult). The remaining 0.x releases harden
rather than extend: torn-page and corruption fuzzing, alignment edge cases, and
the formal API freeze at 0.5.0.

## Breaking changes

**None.** Everything is additive. The page format, file API, pool API, and
on-disk layout from 0.3 are unchanged.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo audit
cargo deny check
cargo bench --bench page_bench

# concurrency model checks (slow; not part of the default run)
RUSTFLAGS="--cfg loom" cargo test --lib --release loom_
```

All green on both platforms. Counts at this tag:

- 36 unit tests (including the pool and allocator property tests)
- 7 integration tests (4 property, 2 Direct I/O, 1 end-to-end)
- 12 doctests
- 3 loom model checks

Criterion numbers (development machine, Windows x86_64, 4 KiB pages):

- `allocate` extending the high-water mark: ~8 ns.
- `allocate` + `free` recycling a freed id: ~16 ns.
- `fetch` cache hit: ~35 ns; miss with eviction: ~2.6 µs.
