# page-db v0.5.0 — Hardening, and the API Freeze

**Fuzzed, hardened, and frozen for 1.0.** v0.5.0 turns the fuzzer loose on the
parse and recovery paths, fixes the one real bug it surfaced — a
denial-of-service on a corrupt allocator superblock — and freezes the public API.
What ships now is what ships at 1.0; the rest of the road is integration soak and
the on-disk-format freeze. No API changes.

## What is page-db?

The paging substrate beneath B-tree and heap storage engines: fixed-size pages
on disk, each checksummed and carrying an LSN slot, read and written through
cross-platform Direct I/O; a buffer pool with pinning and dirty tracking on top;
and a page-id allocator beside it. v0.5.0 adds no new surface — it hardens what
the v0.2–v0.4 releases built.

## What's new in 0.5.0

### Fuzzing the parse and recovery paths

A standalone `fuzz/` harness (cargo-fuzz) drives arbitrary bytes into the two
places page-db parses untrusted input:

- **`page_parse`** feeds arbitrary bytes to `Page::from_bytes` and `crc32c`. A
  page that verifies must round-trip through `to_checksummed_bytes` and back.
- **`allocator_open`** hands `PageAllocator::new` an adversarial superblock and
  free-list chain — a store that returns the fuzzer's bytes directly, modeling a
  checksum-valid but maliciously crafted superblock.

Both run clean across millions of executions: no panic, no hang, no
over-allocation.

### The bug the fuzzer found: a corrupt-superblock DoS

The allocator rebuilds its in-memory free-list by walking the on-disk chain when
it opens. The original walk trusted the superblock's recorded free count and
followed links blindly — so a crafted superblock with a cycle in the chain and a
large free count could drive an unbounded walk: a denial-of-service on a corrupt
file.

The walk is now bounded against exactly that. It never collects more links than
the recorded count, every link must be a real allocated id (`1..high_water`, and
never the reserved page 0), and a repeated id is treated as a cycle and rejected
rather than followed. Its time and memory are bounded by the pages that actually
exist; anything inconsistent is `InvalidSuperblock`. Three unit tests cover the
cycle, out-of-range, and count-mismatch cases, and the fuzzer confirms the rest.

```rust
use page_db::{PageAllocator, DEFAULT_PAGE_SIZE};

# fn main() {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
// A corrupt page 0 is rejected, never trusted — a bad checksum surfaces as a
// page-integrity error, a checksum-valid but malformed superblock as
// `InvalidSuperblock`, and a cyclic or inconsistent free-list likewise.
# std::fs::write(&path, vec![0xFFu8; 4096]).unwrap();
let opened = PageAllocator::open(&path, DEFAULT_PAGE_SIZE);
assert!(opened.is_err());
# }
```

### Alignment edge cases

A dedicated test pins down the page-size contract: `PageSize` accepts exactly the
powers of two in `4096..=1 MiB` and rejects every boundary around them; every
accepted size round-trips in memory and through the file at a page-aligned
offset. Direct I/O is exercised across 4 KiB through 64 KiB pages (added in
0.4.0), confirming the buffer, length, and offset stay block-aligned as the size
changes.

## API freeze

The public API is **frozen for 1.0**. No further additions before 1.0 — only bug
fixes and the on-disk-format freeze. The frozen surface:
[`PageFile`](../API.md#pagefile)/[`PageFileOptions`](../API.md#pagefileoptions),
[`BufferPool`](../API.md#bufferpool)/[`PageGuard`](../API.md#pageguard-pageref-pagemut)/`PageRef`/`PageMut`,
[`PageAllocator`](../API.md#pageallocator), [`PageStore`](../API.md#pagestore),
[`Page`](../API.md#page), the value types, the constants, and
[`PageError`](../API.md#pageerror--pageresult). `cargo audit` and
`cargo deny check` are clean.

## Breaking changes

**None.** The fix to the free-chain walk is internal; it only rejects superblocks
that were already corrupt. The page, file, pool, and allocator APIs and the
on-disk layout are unchanged from 0.4.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo audit
cargo deny check
cargo bench --bench page_bench

# concurrency model checks
RUSTFLAGS="--cfg loom" cargo test --lib --release loom_

# fuzzing (nightly + cargo-fuzz; Linux/macOS)
cargo +nightly fuzz run page_parse     -- -max_total_time=60
cargo +nightly fuzz run allocator_open -- -max_total_time=60
```

All green on both platforms. Counts at this tag:

- 39 unit tests (including the pool and allocator property tests and the three
  corrupt-superblock tests)
- 10 integration tests (4 property, 2 Direct I/O, 3 alignment, 1 end-to-end)
- 12 doctests
- 3 loom model checks
- 2 fuzz targets (`page_parse`, `allocator_open`), each clean over millions of
  executions
