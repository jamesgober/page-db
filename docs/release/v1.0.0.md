# page-db v1.0.0 — Stable

**The first stable release.** page-db is the paging substrate beneath B-tree and
heap storage engines: fixed-size pages on disk, each checksummed and carrying an
LSN slot, read and written through cross-platform Direct I/O; a buffer pool with
pinning and dirty tracking on top; and a page-id allocator beside it. With 1.0
the public API is frozen until 2.0 and the on-disk format is frozen for the 1.x
line — a file written by any 1.x release reads back identically on any other.

There are no API or on-disk changes since 0.5.0. 1.0.0 is the commitment to a
surface built, measured, and hardened across the 0.x series.

## What page-db gives you

A storage engine needs one unglamorous layer underneath it: durable, checksummed,
fixed-size pages, cached in memory, addressable by id. Most engines bury that
layer in their own code; page-db publishes it as a clean, composable primitive so
a B-tree, a heap store, and the index engine above can share one well-tested
implementation.

- **Fixed-size pages with integrity built in.** A 32-byte header carries a magic
  number, a format version, the page id, an LSN slot for write-ahead-log
  coordination, and a CRC32C over the whole page. Every read verifies the header,
  the checksum, and the slot id before the page is handed back — a torn, corrupt,
  or misdirected page is a typed error, never silent bad data.
- **Cross-platform Direct I/O.** Pages bypass the OS page cache — `O_DIRECT` on
  Linux, `F_NOCACHE` on macOS, `FILE_FLAG_NO_BUFFERING` on Windows — into buffers
  aligned to the page size, with a buffered fallback for filesystems that reject
  it. Durability is explicit and platform-correct: `write_page` places bytes,
  `sync` makes them durable with `fdatasync`, `FlushFileBuffers`, or macOS
  `F_FULLFSYNC`.
- **An LRU buffer pool with pinning and dirty tracking.** A bounded frame cache
  with clock eviction. A `fetch` returns a guard that pins the page — a pinned
  page is never evicted — and writing through it marks the page dirty, which is
  always flushed before its frame is reused. Both invariants are loom-checked.
- **A page-id allocator.** Hands out unused ids and reclaims freed ones through an
  on-disk free-list. `allocate` and `free` are pure in-memory operations, and it
  composes with the pool over one shared file via `Arc`.
- **A pluggable backend.** File-backed by default, with a `PageStore` trait so the
  pool and allocator can be driven by an in-memory or alternative store.

## The common case

```rust
use std::sync::Arc;
use page_db::{BufferPool, PageAllocator, PageFile, DEFAULT_PAGE_SIZE};

# fn main() -> Result<(), page_db::PageError> {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
let store = Arc::new(PageFile::open(&path, DEFAULT_PAGE_SIZE)?);
let alloc = PageAllocator::new(Arc::clone(&store))?;   // picks ids
let pool = BufferPool::new(Arc::clone(&store), 256);    // caches pages

let id = alloc.allocate()?;
{
    let guard = pool.new_page(id)?;
    guard.write().payload_mut()[0] = 0x7;
}
pool.flush_all()?;   // dirty frames to the file
alloc.sync()?;       // allocator state durable
# Ok(())
# }
```

## Stability guarantees

- **API frozen until 2.0.** Every public item is stable. `PageError` is
  `#[non_exhaustive]` and `PageFileOptions` is a builder, so the surface can grow
  additively within 1.x without a breaking change.
- **On-disk format frozen for 1.x.** The page header and the allocator superblock
  will not change in a backward-incompatible way within 1.x. The normative
  specification is [`docs/ON_DISK_FORMAT.md`](../ON_DISK_FORMAT.md).
- **MSRV 1.85**, Rust 2024 edition. Cross-platform: Linux, macOS, Windows.

## How it was hardened

- **Fuzzing** — a `cargo-fuzz` harness over the two parse paths: arbitrary bytes
  to `Page::from_bytes` and `crc32c`, and an adversarial superblock and free-list
  to the allocator. Fuzzing found and fixed a denial-of-service in the free-chain
  walk on a corrupt superblock; both targets now run clean over millions of
  inputs.
- **Model checking** — loom verifies the buffer pool's pin/evict/dirty invariants
  and the allocator's concurrent-allocation uniqueness under exhaustive
  interleavings.
- **Stress testing** — eight threads drive the allocator and the pool over one
  shared file with the pool far smaller than the working set, then the data is
  verified cold after a reopen.
- **Fault injection** — injected read and write failures, through the `PageStore`
  seam, propagate as `PageError::Io` and never panic or get swallowed.
- **Property tests** — the pool never loses data across arbitrary fetch/dirty
  sequences; the allocator never double-allocates a live id.
- **Benchmarked honestly** — numbers and method in
  [`docs/BENCHMARKS.md`](../BENCHMARKS.md).

The full suite is green on Windows and Linux, on stable and MSRV 1.85, with macOS
covered by the CI matrix.

## Performance, in one line

A buffer-pool cache hit is ~37 ns — about eighty times faster than the ~3 µs miss
it saves; allocation is a pure in-memory ~9 ns; checksumming a 4 KiB page is
~1.4 µs (~2.8 GiB/s), a fraction of the I/O it rides with; and a durable
`write_page` + `sync` is sub-millisecond and disk-bound. Details in
[`docs/BENCHMARKS.md`](../BENCHMARKS.md).

## Upgrading from 0.5.x

Nothing to do. There are no API or on-disk changes from 0.5.0; 1.0.0 only freezes
the surface.
