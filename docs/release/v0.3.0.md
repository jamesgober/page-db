# page-db v0.3.0 — The Buffer Pool

**The cache over the file.** v0.3.0 adds the layer the directives describe: a
bounded in-memory pool of page frames with pinning and dirty tracking, sitting
on top of the v0.2.0 `PageFile`. The engine above asks for a page by id and gets
back a pinned frame; hot pages stay resident, a pinned page is never evicted, and
a dirty page is always flushed before its frame is reused. Those last two are not
just claims — they are property-tested and checked under `loom` across every
thread interleaving. Purely additive: the page and file API from 0.2 is
unchanged.

## What is page-db?

The paging substrate beneath B-tree and heap storage engines. The
[`PageFile`](../API.md#pagefile) is the durable foundation — fixed-size pages on
disk, each checksummed and carrying an LSN slot, read and written through Direct
I/O. The [`BufferPool`](../API.md#bufferpool) is the cache on top, so the layer
above works against memory-resident frames instead of going to disk on every
access.

## What's new in 0.3.0

### `BufferPool` — a bounded cache of pinned frames

`BufferPool<S = PageFile>` keeps a fixed number of frames resident. The default
backing store is the file, so `BufferPool` with no type parameter is a pool over
a `PageFile`; it is generic over [`PageStore`](../API.md#pagestore) so tests and
later backends can drive it too. The common shape:

```rust
use page_db::{BufferPool, PageId, Lsn, DEFAULT_PAGE_SIZE};

# fn main() -> Result<(), page_db::PageError> {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
let pool = BufferPool::open(&path, DEFAULT_PAGE_SIZE, 256)?;   // 256 frames

// Create a page; writing through the guard marks the frame dirty.
{
    let guard = pool.new_page(PageId::new(0))?;
    guard.write().set_lsn(Lsn::new(1));
}
pool.checkpoint()?;   // flush dirty frames, then make the file durable

// Fetch it — a cache hit, served without I/O.
let guard = pool.fetch(PageId::new(0))?;
assert_eq!(guard.read().lsn(), Lsn::new(1));
# Ok(())
# }
```

Every method takes `&self`, so the pool is shared across threads behind an `Arc`
with no outer lock.

### Pinning and the `PageGuard`

[`fetch`](../API.md#bufferpool) and [`new_page`](../API.md#bufferpool) return a
[`PageGuard`](../API.md#pageguard-pageref-pagemut): an RAII pin. While the guard
is alive the page is resident and unevictable; dropping it releases the pin.
`guard.read()` borrows the page (concurrent readers allowed), `guard.write()`
borrows it exclusively and marks it dirty. If every frame is pinned, admission
returns [`BufferPoolExhausted`](../API.md#pageerror--pageresult) rather than
evicting a page it must not — the pin is a hard guarantee, not a hint.

### Dirty tracking and eviction

Eviction is the clock (second-chance) algorithm: each frame carries a reference
bit set when it is touched; the clock hand sweeps frames, clearing set bits and
skipping pinned ones, and reuses the first unset, unpinned frame. When the victim
is dirty it is written to the store before its buffer is recycled, so no
modification is ever dropped. Frame buffers are allocated once, at construction,
and recycled in place — a cache miss does no allocation, reading the new page
directly into the reclaimed frame through the new `PageFile::read_into`.

### Verifying the invariants

The two rules the directives call out are tested directly, not assumed:

- A **property test** runs arbitrary sequences of fetches and dirtying writes
  against a pool smaller than its working set and asserts every page always reads
  back its last written value — nothing is lost to eviction, nothing goes stale.
- **`loom` model checks** explore every interleaving of two concurrent threads
  and confirm a pinned page is never evicted, and that an evicted dirty page is
  flushed to the store before its frame is reused.

For v0.3.0 the pool serializes its bookkeeping and its miss-path I/O under a
single mutex. That keeps the pin/evict/dirty logic small enough to verify
exhaustively with loom; sharding the table to remove the single-lock bottleneck
is a later, measured change behind the same API.

## Breaking changes

**None.** Everything is additive. The page format, the file API, and the on-disk
layout are unchanged from 0.2.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo audit
cargo deny check
cargo bench --bench page_bench

# concurrency model checks (slow; not part of the default run)
RUSTFLAGS="--cfg loom" cargo test --lib --release loom_
```

All green on both platforms. Counts at this tag:

- 29 unit tests (including the pool property test)
- 5 integration tests (4 property tests, 1 Direct I/O round-trip)
- 11 doctests
- 2 loom model checks

Criterion numbers (development machine, Windows x86_64, 4 KiB pages):

- `fetch` cache hit (resident page, no I/O): ~35 ns.
- `fetch` miss with eviction (clock victim flushed, page read back): ~2.6 µs,
  in line with a raw file read.

The hit path is roughly seventy times faster than the miss — which is the whole
point of the pool.
