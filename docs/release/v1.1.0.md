# page-db v1.1.0: review fixes

An independent review of 1.0.0 found that the buffer pool could lose a write,
could deadlock a checkpoint against latch coupling, and had no way to keep the
write-ahead rule on eviction, and that the allocator could be made unopenable by
a double free or by one torn superblock write. 1.1.0 fixes all of them. There is
no breaking API change and no MSRV change, and the on-disk format stays 1.x:
files written by 1.0 open in 1.1, and files written by 1.1 open in 1.0.

## What changed

### Buffer pool

- **No lost writes.** A write that overlapped a flush of the same page could end
  up on a frame the flush had just marked clean, and eviction then dropped it.
  The dirty bit now changes only under the page lock, so the write is either in
  that flush or left dirty for the next.
- **No checkpoint deadlock.** Flushes no longer wait on a page lock while holding
  the pool mutex. A thread can hold one page's write borrow and fetch another
  page (latch coupling down a B-tree) while a checkpoint runs, and fetches
  continue during the checkpoint. Pages are flushed in page-id order.
- **The write-ahead rule.** Install a `LogWatermark` and the pool never writes a
  page whose LSN is beyond the log's durable point:

  ```rust
  use std::sync::Arc;
  use std::sync::atomic::{AtomicU64, Ordering};
  use page_db::{BufferPool, Lsn, PageError, DEFAULT_PAGE_SIZE};

  fn open_pool(durable: Arc<AtomicU64>) -> Result<BufferPool, PageError> {
      // `durable` is advanced by whatever syncs the log.
      Ok(BufferPool::open("data.pages", DEFAULT_PAGE_SIZE, 256)?
          .with_log_watermark(move || Lsn::new(durable.load(Ordering::Acquire))))
  }
  ```

  Eviction passes over a page the log is not durable for. Implement
  `LogWatermark::force` and the pool forces the log instead: a flush forces it
  before writing such a page, and eviction forces it when every unpinned frame
  is held back. Without a watermark the pool behaves exactly as in 1.0.
- **`BufferPool::discard`** drops a page without writing it. Call it before
  freeing the page with the allocator, so a stale frame cannot overwrite the
  free-list link written into the page.
- **Sticky sync failures.** After a failed `sync` or `checkpoint`, every later
  sync on the pool (and on a `PageFile`) fails, because the OS may already have
  dropped the pages it could not write. Reopen and recover from the log.

### Allocator

- **Double free refused.** Freeing an id that is already free returns
  `InvalidPageId`; before, the id was handed to two owners and the file could not
  be reopened after the next sync.
- **Two superblock copies.** Page 0 now also holds copy A (first sector) and copy
  B (second half), each with a generation number, a checksum of the free-list,
  and its own CRC32C, in bytes 1.0 writes as zero and ignores. `sync` syncs the
  free-list links, then writes copy B and syncs, then writes copy A and the 1.0
  fields and syncs. Opening picks the newest copy whose free-list checks out, so
  a torn page 0 opens. If no copy's free-list checks out, the allocator opens
  with the newest high-water mark and an empty free-list: the free pages leak
  but are never handed out twice, and `free_list_dropped()` reports it.
- **`PageAllocator::from_state`** rebuilds an allocator from a high-water mark
  and free-list kept by the write-ahead log.
- `sync` writes only the free-list links that changed since the last sync.

### Files

- A page id whose byte offset does not fit in 64 bits is `InvalidPageId`
  instead of a debug panic or a release-mode write over a low page.
- The first successful `sync` of a newly created file flushes its parent
  directory on Unix, so the file's name is durable.

## Compatibility

- **API:** additions only (`LogWatermark`, `BufferPool::with_log_watermark`,
  `BufferPool::discard`, `PageAllocator::from_state`,
  `PageAllocator::free_list_dropped`, `PageError::PagePinned`). `PageError` is
  `#[non_exhaustive]`, so the new variant is not a breaking change.
- **Behaviour:** a second `free` of the same id is now an error; a sync after a
  failed sync is now an error; with no watermark installed, eviction and flush
  behave as before.
- **On disk:** the page header and the 1.0 superblock fields are unchanged; the
  new records sit in bytes 1.0 leaves zero. A 1.0 reader of a 1.1 file reads the
  1.0 fields, which always hold the newest committed state. See
  [`docs/ON_DISK_FORMAT.md`](../ON_DISK_FORMAT.md).
- **MSRV:** 1.85, unchanged.

## Upgrading from 1.0.x

Bump the version. To get the write-ahead rule, add `with_log_watermark`. If you
pair the allocator with a pool, call `pool.discard(id)` before `alloc.free(id)`.
Do not retry a checkpoint after a failed sync on the same handle; reopen.

```toml
[dependencies]
page-db = "1.1"
```

## Still open

Fetch misses and dirty-victim writes still run under the pool mutex, the CRC is
software only, and a `PageStore` outside the crate cannot stamp or verify a page
id. They are tracked for a later 1.x release.
