# page-db v0.2.0 — Page Format and Direct I/O

**The first working release.** v0.2.0 turns the scaffold into a durable page
store: a fixed-size page with a checksummed, LSN-bearing header, and a
`PageFile` that reads and writes those pages through cross-platform Direct I/O.
The four-call core — `open`, `allocate_page` / `write_page`, `read_page`,
`sync` — is here, with CRC32C integrity, slot-id verification, and a buffered
fallback for filesystems that reject `O_DIRECT`. The buffer pool, pinning, and
the allocator follow across the rest of the 0.x series.

## What is page-db?

The paging substrate beneath B-tree and heap storage engines. It owns the
get-it-exactly-right layer every database needs: fixed-size pages on disk, each
carrying a header with a CRC32C integrity check and an LSN slot for
write-ahead-log coordination, read and written through Direct I/O that bypasses
the OS page cache. The engine above asks for a page by id and gets back a
checksummed frame; a corrupt or misdirected page comes back as a typed error,
never as silent bad data.

## What's new in 0.2.0

### The page — `Page`

A `Page` is a fixed-size block over a single buffer aligned for Direct I/O, so
it reads into and writes from a file with no intermediate copy. The 32-byte
header is little-endian on disk — magic, version, page id, LSN, and a CRC32C
over the whole page — followed by the payload the layer above owns.

```rust
use page_db::{Page, PageSize, Lsn};

let mut page = Page::new(PageSize::new(4096)?);
page.set_lsn(Lsn::new(42));
page.payload_mut()[..3].copy_from_slice(b"abc");

// Frame it to a checksummed block and load it back, verified.
let bytes = page.to_checksummed_bytes();
let loaded = Page::from_bytes(PageSize::new(4096)?, &bytes)?;
assert_eq!(loaded.lsn(), Lsn::new(42));
# Ok::<(), page_db::PageError>(())
```

The checksum is deliberately not maintained on every mutation — it is stamped
once, on write, and verified once, on read. Rechecksumming after each `set_lsn`
or payload edit would be wasted work.

### The file — `PageFile`

`PageFile` is an array of pages on disk addressed by `PageId`: page `n` occupies
bytes `n * page_size .. (n+1) * page_size`. The common case is four calls.

```rust
use page_db::{PageFile, PageId, Lsn, DEFAULT_PAGE_SIZE};

# fn main() -> Result<(), page_db::PageError> {
# let dir = tempfile::tempdir().unwrap();
# let path = dir.path().join("data.pages");
let file = PageFile::open(&path, DEFAULT_PAGE_SIZE)?;

let mut page = file.allocate_page();
page.set_lsn(Lsn::new(1));
page.payload_mut()[..5].copy_from_slice(b"hello");
file.write_page(PageId::new(0), &mut page)?;   // place the bytes
file.sync()?;                                   // make them durable

let got = file.read_page(PageId::new(0))?;      // header + checksum verified
assert_eq!(&got.payload()[..5], b"hello");
# Ok(())
# }
```

Reads and writes are positioned and take `&self` — there is no shared file
cursor — so the handle is shared freely across threads, the signature the buffer
pool will keep when it lands on top.

### The durability contract, made explicit

`write_page` returns when the bytes are placed; `sync` returns when they are on
stable storage. They are separate calls because the cost gap between them is the
difference between a usable database and a slow one. Batch many writes, then sync
once.

The flush is platform-correct, which is not the same call everywhere — Linux
`fdatasync`, Windows `FlushFileBuffers`, and on macOS `fcntl(F_FULLFSYNC)`, not
plain `fsync` (which leaves data in the drive's own write cache).

### Cross-platform Direct I/O

Direct I/O bypasses the OS page cache so the buffer pool above is the single
authority on what is resident — `O_DIRECT` on Linux, `F_NOCACHE` on macOS,
`FILE_FLAG_NO_BUFFERING | FILE_FLAG_WRITE_THROUGH` on Windows. Page buffers are
aligned to the page size, which satisfies every supported platform's block
alignment rule for page sizes of 4 KiB and up. Where a filesystem rejects
Direct I/O (some overlay and network mounts), `PageFileOptions::direct_io(false)`
selects buffered I/O — the same API and the same durability via `sync`, an
explicit choice rather than a silent fallback.

### Integrity — CRC32C and slot verification

Every page is checksummed with CRC32C (Castagnoli), the variant CPUs accelerate
and the one the sibling `wal-db` uses. On read, the magic, the version, the
checksum, and the stamped slot id are all checked before the page is returned —
so a torn write, bit rot, or a misdirected read surfaces as
`ChecksumMismatch` / `MisdirectedPage` rather than corrupting the layer above. A
property test asserts that *any* single-byte corruption of a stored page is
caught on read.

The checksum is a portable software slice-by-eight table with const-generated
lookup tables — no `unsafe`, no CPU feature detection, identical on every target.
At ~2.9 GiB/s on a 4 KiB page it is a fraction of the I/O it rides with, so a
hardware-accelerated variant is a measured optimization for later, not a guess
made now.

### Errors — `PageError`

A domain error type (`thiserror`), `#[non_exhaustive]`, that splits into I/O
failures (`Io`, preserving the source `io::Error`) and integrity failures
(`ChecksumMismatch`, `MisdirectedPage`, `BadMagic`, `UnsupportedVersion`,
`ShortRead`, `InvalidPageSize`). Reading an unwritten slot is a `ShortRead`, not
a panic.

## Breaking changes

**Relative to the 0.1 scaffold, yes — and intentionally.** 0.1 shipped no
functional code, only structure, so none of this breaks a real consumer:

- The crate is now `std`-only. The scaffold's `no_std` posture and `std` feature
  flag are gone — a file-backed, Direct-I/O store is inherently `std`. The
  default feature set is now empty; `serde` remains opt-in for `PageId` and
  `Lsn`.
- The checksum is CRC32C, not the IEEE CRC32 the scaffold's prose implied.

**On-disk format is unstable across 0.x.** Files written by 0.2 are not
guaranteed readable by later 0.x releases; the format is documented in the
header table and frozen for 1.x before 1.0.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable 1.95.x and MSRV
1.85.0; macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo audit
cargo deny check
cargo bench --bench page_bench
```

All green on both platforms. Counts at this tag:

- 21 unit tests
- 5 integration tests (4 property tests, 1 Direct I/O round-trip)
- 8 doctests

Criterion numbers (development machine, Windows x86_64, 4 KiB pages):

- CRC32C over a 4 KiB page: ~1.29 µs (~2.95 GiB/s).
- `write_page` (frame + checksum + buffered write, no flush): ~2.7 µs.
- `read_page` (buffered read + full verification): ~2.5 µs.
- `write_page` + `sync` (one page made fully durable): ~0.9 ms, dominated by the
  disk flush.

These are honest starting points; the cache that will absorb most reads is the
work of 0.3.

## What's next

- **0.3.0 — Buffer pool.** A bounded LRU frame cache over `PageFile`, with
  pinning (a pinned page is never evicted) and dirty tracking (a dirty page is
  never dropped without a flush) — both as property-tested invariants — and
  benchmarks for the cache hot paths.
